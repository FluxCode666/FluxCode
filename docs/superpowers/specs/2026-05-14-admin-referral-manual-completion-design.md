# 推广管理手动完成与奖励分账设计

> **日期**：2026-05-14
> **状态**：待评审
> **范围**：管理端推广列表、管理端推广接口、推广奖励发放链路、充值/奖励日志拆分

## 1. 背景

推广管理页中的推广列表需要提供一个人工兜底能力，用于支付回调失败但用户实际上已经完成支付的极端场景。

当前问题不止是缺一个“手动完成”按钮，还包括现有首充链路里“充值本体额度”和“推广奖励额度”存在混合发放、混合记录的问题。这会导致：

- 用户无法清晰区分自己充值所得和推广奖励所得
- 管理端和财务侧难以审计每一笔推广奖励
- 手动兜底时无法安全地只补发推广侧权益

因此，这次改动需要同时完成：

- 在推广列表中新增手动完成入口
- 让手动完成只补发推广侧权益，不补发支付主链路权益
- 将充值本体与推广奖励彻底分账、分日志记录

## 2. 目标

### 2.1 功能目标

1. 管理端可在推广列表中对 `pending` 推广记录执行“手动完成”
2. 手动完成后，推广记录状态变为 `completed`
3. 手动完成时，需要补发“推广完成时本该发放的推广侧奖励”
4. 手动完成时，不得补发支付主链路奖励
5. 推广列表中的“推广人”列改为展示“ID tag + 邮箱”

### 2.2 账务目标

1. 用户充值本体与推广奖励必须分开记账
2. 推广奖励额度、推广现金奖励、销售返佣现金必须有独立日志
3. 手动完成只依赖现有充值/额度/现金日志体系，不新增单独管理员审计表

## 3. 非目标

以下内容不在本次范围内：

- 不支持把 `completed` 改回 `pending`
- 不支持任意状态互改
- 不支持通过手动完成补发充值本体额度
- 不支持通过手动完成补开订阅本体
- 不新增一套独立的“管理员操作日志”表

## 4. 页面设计

## 4.1 推广列表改动

列表新增一列“操作”，并调整“推广人”列的展示方式。

### 推广人列

当前展示为纯 ID。调整后展示为：

- 前置一个 tag，内容为 `#<referrer_id>`
- tag 右侧展示推广人邮箱
- 如果邮箱为空，则降级为仅展示 `#<referrer_id>`

示例：

```text
[ #123 ]  alice@example.com
```

### 操作列

- 仅当记录状态为 `pending` 时显示“手动完成”按钮
- `completed` 记录不显示按钮
- 点击按钮后弹出确认框
- 确认框中要求管理员填写备注，说明手动完成原因

建议提示语义：

- 该操作用于支付回调失败后的人工兜底
- 不会补发充值本体或订阅本体
- 会补发该推广记录应得的推广奖励

### 交互结果

- 成功后刷新当前列表
- 该记录状态更新为 `completed`
- 操作按钮消失

## 5. 后端接口设计

新增管理端接口：

```http
POST /api/v1/admin/referral/:id/mark-completed
```

请求体：

```json
{
  "notes": "支付回调失败，人工补完成推广奖励"
}
```

返回体：

```json
{
  "message": "ok"
}
```

### 请求约束

- `id` 必须为合法推广记录 ID
- `notes` 必填，去除首尾空白后不能为空

## 6. 业务规则

### 6.1 状态约束

接口只允许：

```text
pending -> completed
```

若记录不是 `pending`，直接返回错误，避免重复补发推广奖励。

### 6.2 手动完成补发范围

手动完成时，补发范围为“该推广记录完成时本该发放的推广侧权益”，包括但不限于：

- 被邀请人推广奖励额度
- 邀请人推广奖励额度
- 推广现金奖励
- 销售用户返佣现金
- 其他当前推广完成链路中定义为“推广侧”的奖励

### 6.3 手动完成不补发范围

以下主支付链路权益不得由该接口补发：

- 用户充值本体额度
- 用户订阅本体开通
- 与支付主单成功强绑定、但不属于推广侧的其他权益

## 7. 关键实现原则：支付主链路与推广奖励链路拆分

这是本次设计最重要的约束。

现有链路中，如果“首充成功”把“充值本体额度”和“推广奖励额度”在一次处理里一起发放、一起记账，那么实现上必须拆开。

目标不是简单复用旧逻辑，而是把逻辑拆为清晰的几个阶段：

1. 支付主链路权益发放
2. 支付主链路日志记录
3. 推广奖励发放
4. 推广奖励日志记录
5. 推广记录状态更新

这样正常支付成功和管理员手动完成才能共享“推广奖励发放”能力，但不会共享“充值本体发放”副作用。

### 示例

假设被拉新用户首充 20 美元额度，按推广规则还应获得 10 美元推广奖励额度。

正确结果必须是：

1. 用户先收到 20 美元充值本体额度
2. 产生一条充值本体相关日志
3. 用户再收到 10 美元推广奖励额度
4. 产生一条推广奖励相关日志

而不能是：

- 直接一次性给用户记 30 美元
- 只留一条混合日志

销售返佣现金也必须遵循同样原则：独立计算、独立落账、独立日志。

## 8. 日志与审计要求

本次不新增单独管理员操作日志表，但必须确保推广相关发放全部落入现有日志体系。

### 8.1 充值本体

充值本体必须继续使用现有充值/额度日志体系，单独记录。

### 8.2 推广奖励额度

推广奖励额度必须有独立额度日志，不能混入充值本体日志。

### 8.3 推广现金奖励

推广现金奖励必须有独立现金日志，能够区分其来源是推广奖励。

### 8.4 销售返佣现金

销售返佣现金必须有独立现金日志，能够区分其来源是销售返佣。

### 8.5 手动完成备注

虽然不新增管理员操作日志表，但本次手动完成提交的 `notes` 仍需落到现有可追踪体系中。优先方式：

- 作为相关推广奖励日志的备注字段写入
- 或者写入推广记录的备注字段，供后续排查

具体采用哪一种，以当前代码中已有字段和记录模型为准，优先复用现有结构。

## 9. 数据与模型调整

为了支持本次功能，预计需要补齐以下数据能力：

1. 推广列表查询返回推广人邮箱
2. 推广记录支持保存手动完成备注，若现有结构无合适字段则补字段
3. 推广奖励发放逻辑需要能区分：
   - 充值本体额度
   - 推广奖励额度
   - 推广现金奖励
   - 销售返佣现金

如果当前日志模型无法表达这些来源，需要在现有日志体系中新增更细的 `type` / `source` / `reason` 枚举值，而不是把多类奖励塞进已有模糊类型。

## 10. 错误处理

接口应覆盖以下错误场景：

- 推广记录不存在
- 推广记录状态不是 `pending`
- 备注为空
- 推广奖励重复发放风险校验失败
- 推广奖励发放过程中出现数据库或业务错误

错误时要求：

- 不更新推广状态
- 不留下部分成功、部分失败的混乱状态

因此，手动完成相关更新应在事务内完成，保证原子性。

## 11. 测试策略

### 11.1 后端测试

至少覆盖：

1. `pending` 记录可成功手动完成
2. `completed` 记录不能再次手动完成
3. 手动完成不会补发充值本体额度
4. 手动完成会补发推广奖励额度
5. 手动完成会补发推广现金奖励
6. 手动完成会补发销售返佣现金
7. 充值本体日志与推广奖励日志分离
8. 推广奖励发放失败时，状态不会被错误更新为 `completed`

### 11.2 前端测试

至少覆盖：

1. 推广人列正确展示 `ID tag + 邮箱`
2. `pending` 行显示“手动完成”按钮
3. `completed` 行不显示按钮
4. 提交空备注时阻止发送请求
5. 接口成功后列表正确刷新

## 12. 实施建议

建议按以下顺序实施：

1. 先梳理并拆分现有支付成功后的奖励发放逻辑
2. 明确充值本体日志与推广奖励日志的现有落点
3. 新增“手动完成”管理端接口
4. 扩展推广列表查询结果，返回推广人邮箱
5. 修改前端列表展示与交互
6. 补齐测试

这样做可以先把后端账务边界理顺，再挂管理端入口，避免前端按钮做好了、后端仍然沿用旧耦合逻辑。

## 13. 方案结论

本次改动的本质不是“给推广列表加一个按钮”，而是：

- 为推广记录提供安全的人工完成入口
- 让人工完成只触发推广侧权益
- 把充值本体与推广奖励彻底拆账
- 让推广额度奖励、推广现金奖励、销售返佣现金都能被单独追踪

只有在这些边界都明确且可审计的前提下，手动兜底才是可长期维护的能力。
